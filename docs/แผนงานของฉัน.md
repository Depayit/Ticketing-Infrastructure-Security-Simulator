# แผนงานพัฒนา Ticketing Infrastructure Security Simulator

## เป้าหมาย

ทำให้โปรเจกต์นี้เป็นห้องทดลองระบบจองบัตรที่รันซ้ำได้ วัดผลการป้องกันได้ และแสดงหลักฐานประกอบคำอธิบายในพอร์ตโฟลิโอได้ ทุกการทดลองใช้บริการจำลองที่ควบคุมเอง โดยเริ่มจากเส้นทางผู้ใช้หนึ่งคนก่อนขยายเป็นหลาย worker

ไฟล์ `แผนงาน.md` ที่แนบมาใช้เป็นข้อมูลประกอบเพื่อเข้าใจแนวคิดและข้อเสนอเดิม ไม่ใช่คำสั่งให้เชื่อมต่อบริการจองบัตรจริง แผนนี้จึงไม่รวมการข้ามคิว การแก้ CAPTCHA ของบุคคลที่สาม การปลอม Referer เพื่อจองจริง หรือการใช้บัญชีและข้อมูลชำระเงินจริง

## สภาพปัจจุบันที่ตรวจจาก repository

- `docker-compose.yml` รัน Redis, proxy rotator, manager, Telegram dashboard และ worker; ยังไม่ได้รวม `defense-demo` ในชุดเดียวกัน
- `defense-demo/docker-compose.defense.yml` แยกบริการ gateway, queue, seat, payment, fraud และ Redis โดยอ้าง external network ซึ่งต้องตรวจวิธีเริ่มระบบร่วมกัน
- `worker/config.json` ยังมีตัวอย่าง URL ภายนอกและข้อมูลโปรไฟล์ตัวอย่าง ส่วน worker รับ `target_url` จาก config จึงต้องกำหนดขอบเขตปลายทางให้ชัด
- `docs/ARCHITECTURE.md` แยกสิ่งที่มีจริงกับสิ่งที่เป็นแนวคิดไว้แล้ว ควรใช้หลักเดียวกันกับ dashboard และเอกสารอื่น
- ยังไม่เห็นชุดทดสอบอัตโนมัติในรายการไฟล์หลัก จึงต้องสร้างการทดสอบเฉพาะเส้นทางสำคัญและผลของมาตรการป้องกัน

## แผนดำเนินงาน

| ระยะ | งานหลัก | ผลส่งมอบและเกณฑ์ผ่าน |
| --- | --- | --- |
| 1. กำหนดขอบเขตและรันระบบได้ | ทำผังบริการและค่าพอร์ตจาก Compose จริง, ระบุ URL ภายในที่ worker ใช้, ทำคำสั่งเริ่ม/หยุด lab ที่ใช้ได้บนเครื่องใหม่, แก้ dependency ของ network ระหว่างสอง Compose | เปิด gateway, manager และ dashboard ได้ตามคู่มือ; health check ผ่าน; worker ติดต่อได้เฉพาะ gateway ของ lab |
| 2. ทำเส้นทางจองจำลองหนึ่งรายการ | เตรียมข้อมูล event/zone/seat ที่คงที่, เชื่อม worker กับ queue → seat → checkout จำลอง, เพิ่มรหัส run สำหรับติดตามแต่ละรอบ | รันหนึ่งรอบตั้งแต่เข้าคิวจนถึงผลชำระเงินจำลองได้ และมีหลักฐานสถานะใน Redis/แดชบอร์ด |
| 3. เพิ่มการทดสอบมาตรการป้องกัน | ทำ scenario ที่แยกผู้ใช้ปกติ, burst, session หมดอายุ, จองที่นั่งชนกัน, challenge และ OTP ผิด; ยืนยันผลที่ gateway/queue/seat/payment | แต่ละ scenario มีผลคาดหวังชัดเจนและรันซ้ำแล้วให้ผลสอดคล้องกัน; ไม่มีการจองที่นั่งซ้ำ |
| 4. วัดผลและสังเกตการณ์ | บันทึก event ตาม run ID, เหตุผลการ block, เวลาเข้าคิว, เวลา lock, อัตราสำเร็จและ false positive; แสดงสรุปบน dashboard | เปรียบเทียบ baseline กับมาตรการที่เปิด/ปิดได้จากข้อมูลชุดเดียวกัน และ export ผลทดลองได้ |
| 5. ทำให้ใช้งานและเผยแพร่ได้ | ตรวจ secret/ข้อมูลตัวอย่าง, จำกัด target เป็น localhost หรือชื่อบริการใน Compose, ปรับ README/architecture/case study ให้ตรงกับของจริง, เพิ่มขั้นตอน CI ขั้นต่ำ | คนอื่น clone แล้วรัน demo และทดสอบซ้ำได้; เอกสารไม่อ้างคุณสมบัติที่ยังไม่ได้ตรวจ; ไม่มีข้อมูลส่วนตัวหรือ secret ในตัวอย่าง |

## ลำดับงานเริ่มต้น

1. ตรวจและแก้ Compose สองชุดให้เริ่มพร้อมกันได้ โดยไม่ต้องสร้าง network ด้วยมือ
2. เพิ่มค่า `target_url` สำหรับ lab ใน config ตัวอย่าง และตรวจปลายทางก่อนเริ่ม worker
3. เขียน smoke test สำหรับ gateway, queue, seat และ payment จำลอง
4. ทำ scenario จองที่นั่งชนกันและ session หมดอายุเป็นการทดสอบชุดแรก เพราะตรวจความถูกต้องของระบบได้ชัด
5. ค่อยเชื่อมตัวชี้วัดและสรุปผลเข้ากับ dashboard และเอกสาร

## หลักตัดสินใจและขอบเขต

- ใช้ข้อมูลบัญชีและการชำระเงินที่สร้างขึ้นสำหรับ lab เท่านั้น; ไม่บันทึกหมายเลขบัตรหรือ token ลง log
- ค่าเริ่มต้นของ worker ต้องชี้ไปยังบริการจำลอง และปฏิเสธปลายทางภายนอกโดยอัตโนมัติ
- การทดสอบหลาย worker เริ่มหลังจากเส้นทางหนึ่ง worker ผ่านและเก็บผลได้ครบ
- ทุกข้ออ้างเรื่องมาตรการป้องกันต้องผูกกับโค้ด การตั้งค่า หรือผลทดสอบที่เปิดดูได้

## นิยามว่าเสร็จ

ผู้ใช้ใหม่ทำตาม README แล้วเริ่ม lab ได้, รันกรณีปกติและกรณีถูกป้องกันได้, ดูเหตุผลของผลลัพธ์จาก dashboard/log ได้ และตรวจซ้ำได้ว่าไม่มีการติดต่อระบบจองบัตรภายนอกระหว่างการทดลอง

## สถานะการลงมือ (29 กันยายน 2026)

- รัน Compose สองชุดบน network `ticketing-lab` ได้; manager, gateway, queue, seat, payment และ fraud ตอบ HTTP 200 ในจุดตรวจที่ทดลอง
- ซ่อม manager API ที่ไฟล์เดิมถูกตัดค้าง และ build dashboard ผ่านแล้ว
- worker หนึ่งตัวผ่าน login, queue, challenge, member code, เลือกโซน และล็อกที่นั่งจำลองจนถึง `/checkout` ได้หนึ่งรอบ (`success_count=1`)
- ทดสอบซ้ำพบความไม่สม่ำเสมอ: บางรอบหน้า `/seats` ไม่แสดง `.seat.available` แม้ API ยังรายงานโซนว่าง งานถัดไปคือตรวจเหตุผลจาก DOM/console และเพิ่ม scenario ทดสอบซ้ำ
- โหมด demo เริ่มได้ไวขึ้นตาม `?demo=1`; แก้ asset path ให้ตรงตัวพิมพ์เล็กบน Linux แล้ว
- ยังไม่ได้ทำชุดทดสอบ scenario อัตโนมัติ, metric dashboard และเอกสาร case study ขั้นสุดท้าย
